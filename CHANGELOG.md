# Changelog

All notable changes to Aeromux will be documented in this file.

## [0.9.0] — 2026-10-26

### Added

- **REST API: Configuration Endpoint** — `GET /api/v1/config` returns the configuration the daemon is running with, after the built-in defaults, the YAML file and the command-line options are combined, in the same structure as `aeromux.yaml`. `ConfigFile` names the YAML file that was loaded, or is `null` when none was, which answers the common question of why a setting in the file seems to be ignored. With `?source=true`, every value also says where it came from: `Cli`, `Yaml` or `Default`. The receiver UUID is shown as `"(redacted)"`, because MLAT aggregators identify a feeder by it.
- **REST API: Health Check Reports Failing Sources** — `GET /api/v1/health` always answered `OK`, even when the daemon was receiving nothing. It now judges each input: an SDR device fails when it has delivered no samples for 10 seconds, and a Beast source when it has been disconnected for 10 seconds. A quiet sky is not a failure, and MLAT input is not judged. `Status` is `OK` when nothing fails, `Degraded` when some sources fail and at least one still works, and `Unhealthy` when every source fails. `Unhealthy` is answered with HTTP 503, so `curl --fail`, Docker `HEALTHCHECK` and uptime monitors react without reading the body, while `Degraded` keeps 200 so a daemon still receiving through its other inputs is not restarted. The new `Problems` list names each failing source and for how long.
- **REST API: Access from Dashboards on Other Origins (CORS)** — A web page served from somewhere other than the daemon, such as a dashboard on `http://dashboard.local:3000`, could not read the REST API from the browser, because browsers block such reads unless the server allows them. The new `network.apiCorsOrigins` setting, or the repeatable `--api-cors-origin` option, lists the origins allowed to read `/api` from a browser. It is empty by default, which changes nothing, and `*` allows every origin with a warning in the log, because any web page could then read the API, including `/api/v1/config`. The Web Map, served by the daemon itself, and clients such as curl, scripts and Home Assistant are not affected either way.
- **REST API and Logs: Messages by Type for Every Source** — Every SDR device, Beast source and the MLAT input now count their messages by downlink format (DF), ADS-B type code (TC) and Comm-B register (BDS). `/api/v1/stats` reports them as `MessageTypes` on each source, with totals and rates over the last 60 seconds, and the session summary in the log shows them as one table per source, DF, TC and BDS side by side with each code's share. This answers questions the totals cannot: a growing share of TC 0, airborne messages without a position, is how GNSS interference shows when aircraft lose their satellite position. Until now only SDR devices logged such a breakdown, and only at Debug level or when the device stopped.
- **Web Map: Receiver Statistics** — A new chart icon next to the search field opens the receiver's statistics where the settings open: the health with each failing source, the messages of every SDR device, Beast source and the MLAT input, each device's extracted frames split into messages, duplicates and frames not yet confirmed, and the messages by downlink format, type code and Comm-B register, each code with a short name; click a source to see its message types. Every list is drawn as a bar and rows that add up to a total row, so it is visible how the numbers relate. `Now` shows rates over the last minute, `Since start` totals. A dot on the icon turns amber or red when sources are failing, and gray when the daemon does not answer. See the Statistics section of the [Web Map Guide](docs/WEBMAP.md).

### Changed

- **REST API: Statistics Report Each Source, and Only Measurements** — `GET /api/v1/stats` has a new shape, so tools that read it need updating. Every source reports `Messages`, the messages it handed to the aircraft tracker, with `MessagesPerSecond`, and `Messages` at the top adds them up. `Sdr` lists each running device with its samples per second, the frames it extracted, how many needed a single-bit CRC correction, the duplicates it dropped and its messages, each also per second, and the sums of all devices; it is `null` when no SDR device runs. `BeastSources` reports each Beast input with its connection state, since when and its reconnects, `Mlat` the connected mlat-client instances, `Outputs` the clients connected to each TCP output, and `Database` the loaded database version. Rates (`PerSecond`) now cover the last 60 seconds instead of the whole session, so a monitor sees a receiver that stopped a few minutes ago; `Messages.AveragePerSecond` keeps the session average. `Receiver` and `HeatmapCollectionEnabled` moved to `GET /api/v1/config` (as `Receiver`, with `Altitude` instead of `AltitudeMeters`, and `Heatmap.Collect`), and `Devices` and `Stream` are replaced by the sections above. `Stream.CrcErrors` has no successor: despite its name it counted the extracted frames whose aircraft address was not confirmed yet, not frames that failed the CRC check. The "Migrating from 0.8" table in `docs/API.md` lists where each old field went.
- **Logs: Per-Device Final Statistics Replaced by the Session Summary** — Each SDR device logged a block of about seventeen lines of statistics when it stopped. Its figures are now in the session summary (extracted, corrected and duplicate frames, messages), and its diagnostics (confidence tracking, parser validation failures, unsupported messages, deduplication cache) in the Debug lines logged every 10 seconds, where the confidence figures shared by all devices now appear once instead of once per device. The live command also logs its session summary after the receivers have stopped, as the daemon does, so the summary and the session end follow each other directly.
- **Logs and Terminal: Numbers in US Format Everywhere** — The session summary's message type tables, the `live` display and the commands' output formatted numbers with the machine's language, so a share read `23.7%` on one receiver and `23,7%` on another, next to log lines that were always in US format. Numbers are now in US format (`113,588`, `805.7`, `23.7%`) everywhere, whatever the machine's language. Numbers typed on the command line, such as `--tuner-gain 49.6`, are read with a decimal point everywhere too, as the configuration file's always were.

### Fixed

- **Configuration: Empty Configuration File Stopped Aeromux** — An `aeromux.yaml` with nothing in it, or with every line commented out, stopped the daemon and the live display at startup with `Failed to load configuration` and an internal null reference error. Such a file now means what it says: nothing is configured, and every setting keeps its default.
- **Daemon: Port Check Ignored Command-Line Ports** — The daemon refuses ports below 1024, which need administrator rights, but it checked the ports from the YAML file instead of the ones actually used. A port given on the command line, such as `--api-port 80`, slipped past the check and failed later when the port could not be opened, while `--api-port 9000` was refused if the YAML file still said `apiPort: 80`. The check now applies to the port the daemon will listen on, wherever it was set.
- **MLAT: Input Ignored the Bind Address** — The MLAT input, where mlat-client sends the positions it computes (port 30104 by default), always listened on every network interface, even when `bindAddress` or `--bind-address` limited the daemon to one, such as `127.0.0.1` to keep it local. It now listens on the same address as the daemon's other listeners, so an mlat-client running on another machine needs a bind address that machine can reach.
- **Statistics: All Zeros Without an SDR Device** — A daemon receiving only from Beast sources, with or without MLAT, reported zero frames and zero frames per second in `/api/v1/stats`. Beast sources and MLAT now report their own messages, and `Messages.Total` covers every source.
- **Logs: Session Summary Without an SDR Device, Corrected Frames, and Sessions Over a Day** — When the daemon stopped, it wrote no session summary to the log unless an SDR device was running, and the live command wrote "Statistics not available". Both now summarize every source with the figures and names of `/api/v1/stats`: the messages of all sources together, the SDR devices together and each device with its extracted, corrected and duplicate frames, each Beast source, and MLAT, each source with its share of the messages, laid out one value per line with the numbers in one column. The summary's corrected frame count was always 0, because the CRC correction happens before the point it was counted; corrections are now counted where they happen. The session duration counted only the hours of the last day, so a daemon that ran for 25 hours reported `01:00:00`; it now reports `25:00:00`.

## [0.8.4] — 2026-10-25

### Added

- **Tracking: Vertical Rate Source** — The vertical rate an aircraft broadcasts comes either from its GNSS receiver or from its barometric air data, and the two can differ noticeably. The source is now reported as `VerticalRateSource` (`"GNSS"` or `"Barometric"`) in the velocity section of the REST API aircraft detail and the JSON broadcast, and shown as "Vertical Rate Source" in the TUI and the Web Map detail panel.

### Changed

- **Packaging: Service Stays Enabled When Upgrading the Debian Package** — Installing a new `.deb` over an existing installation with `dpkg -i`, or reinstalling the same one, used to stop and disable the `aeromux` service, so it stayed off until it was enabled again with `systemctl enable --now aeromux`. An upgrade now leaves the service enabled, and restarts it if it was running so the new version takes over. Upgrading to 0.8.4 still runs the removal script of the version already installed, so after that one upgrade the service has to be enabled once more.

### Fixed

- **Tracking: Position "Last Update" for Aircraft That Are Not Moving** — An aircraft's position "Last Update", shown in the Web Map detail panel and the TUI and reported as `Position.LastUpdate` by the REST API and the JSON broadcast, only moved when the reported position changed. An aircraft sending positions every second without moving, as many do while parked, hovering or barely moving, appeared to have stopped reporting its position. Worse, after 30 seconds without movement the tracker treated its position as stale and stopped checking new positions against the aircraft's possible speed, so a single corrupted position report could put it many miles away and draw a line across the map. `LastUpdate` now records when a position was last received and accepted, moved or not, which keeps that check working. Surface positions no longer record an update time for messages that carried no usable position.
- **Tracking: VNAV Shown as Approach Mode** — Radars can ask an aircraft for its selected vertical intention (BDS 4,0), a Comm-B reply that includes the autopilot's VNAV, altitude hold and approach mode flags. Aeromux read the VNAV flag as approach mode and the approach flag as VNAV, so an aircraft cruising with VNAV engaged was shown flying an approach in the Web Map detail panel, the TUI, the REST API and the JSON broadcast. For aircraft that also report their autopilot modes over ADS-B, which was read correctly, "Approach Mode" switched between yes and no as the two kinds of message arrived, and aircraft heard only through Comm-B showed approach instead of VNAV. A mode that the Comm-B reply reported as off was also ignored, so once a mode was shown as engaged, only an ADS-B message could clear it. A mode reported as off is now shown as off.
- **Tracking: Comm-B Replies Misread as Weather Hazards or Heading** — A Comm-B reply does not say which register it carries, so Aeromux works it out from the content. Replies from registers it does not decode were often taken for a meteorological hazard report (BDS 4,5) or an air-referenced state vector (BDS 5,3). That showed, for example, an airliner cruising at FL400 in severe turbulence and icing, or replaced an aircraft's magnetic and true heading with a wrong value, in the Web Map detail panel, the TUI, the REST API and the JSON broadcast. A few were also misread as selected vertical intention or heading and speed reports. Each register marks unavailable fields with a status bit and must leave them empty, and Aeromux now rejects a reply that carries data in a field marked unavailable, as ICAO requires. In the recorded traffic used for testing, this removes every BDS 4,5 and 5,3 result, all of them wrong, without losing a genuine report. The vertical rate in BDS 5,3 reports is also decoded with the correct sign, so a slow descent is no longer read as an impossible dive and discarded.
- **Tracking: Aircraft on the Ground Shown Tens of Kilometers Away** — Surface position messages were decoded with the wrong number of longitude zones, and odd-format messages were not given their one zone fewer, so an aircraft at the airport appeared far to its east or west, jumping between two wrong places as the two message formats alternated. At Budapest airport, with a receiver in the city, the error was about 85 to 105 km. Latitude was correct. Surface positions now use the same zone function as airborne positions, as the standard requires, and land where the aircraft is.
- **Tracking: Wrong Taxi Speed, and Surface Positions Lost Above About 8 Knots** — The speed carried in surface position messages was read with a made-up scale, so a taxiing aircraft could show "130-140 kts" at 5 knots, and any speed above about 8 knots made Aeromux discard the whole message, position included. The speed is now decoded from the standard bands, to the middle of each step, and no surface message is discarded for its speed. The movement category reported as `MovementCategory` in the REST API and the JSON broadcast, and shown in the Web Map detail panel and the TUI, now names those bands (for example `"2-15 kts"` or `"15-70 kts"`) instead of the previous labels, which did not match the encoding.
- **Decoding: Most All-Call Replies Discarded** — An all-call reply (DF 11) carries the identifier of the interrogator that asked for it in its checksum, and Aeromux accepted only replies to interrogators with identifier 0. In the recorded traffic used for testing, that discarded 72% of all-call replies and marked others as corrected although nothing was wrong with them. Replies to every interrogator are now accepted, as other decoders do.
- **Tracking: NIC Supplement A Showed the Heading Reference** — The NIC supplement A flag of the operational status message was read from the bit that holds the heading reference, so the Web Map detail panel, the TUI, the REST API and the JSON broadcast showed whether the aircraft reports headings against magnetic north instead. It is now read from its own bit.
- **Tracking: Altitude Ignored When an Aircraft Had No Position** — An aircraft without a position fix still broadcasts its barometric altitude, in a message type that says no position is available. Aeromux discarded that altitude, so such aircraft showed no altitude at all. It is now used like any other barometric altitude, including the GNSS altitude derived from it. In the recorded traffic used for testing, all 231 such messages now give the same altitude as dump1090.
- **Tracking: Gliders, Balloons and Drones Shown as Ground Obstacles** — The emitter category was decoded from an outdated table. Gliders, balloons and parachutists were reported as point, cluster and line obstacles, ultralights, drones and space vehicles as reserved, and point obstacles as surface service vehicles. Categories now follow the DO-260B table, and an aircraft that reports no category shows "No Information" whatever the message type. The `Category` labels in the REST API and the JSON broadcast change accordingly: for example `"Glider / Sailplane"`, `"Lighter-than-air"`, `"Unmanned Aerial Vehicle"`, `"Surface Service Vehicle"` and `"Point Obstacle"`, and `"No Information"` instead of `"No Category"`.
- **Web Map: Generic Icon for Some Aircraft Categories** — When an aircraft's type is not known, the Web Map picks its icon from the emitter category. It looked the category up under a different spelling than the one the API sends, so "High Vortex Large" and "High Performance" aircraft always got the generic icon. They now get their airliner and fast-jet icons, and gliders, balloons, ultralights and drones get their own.
- **Web Map: Business Jets Shown as Airliners** — Business jets the Web Map had no icon of their own for, such as the Pilatus PC-24, Embraer Praetor 500 and 600, Citation Longitude and Gulfstream G200, were drawn as airliners because they share an airliner's wake turbulence category. They now get business jet icons, and the Yak-42 is no longer drawn as a widebody trijet.
- **Tracking: Phantom Aircraft from TIS-B and ADS-R** — Ground stations rebroadcast traffic they see on other systems (TIS-B and ADS-R), sometimes under a track number or an anonymous address instead of an ICAO aircraft address. Aeromux decoded all of these as ordinary aircraft, so a track number could appear as an aircraft that does not exist, or add its data to a real aircraft that happened to have the same address. Only rebroadcasts that carry an ICAO aircraft address are now decoded and tracked. The others are still forwarded on the Beast output. Military extended squitters (DF 19), whose content is not standardized, are no longer decoded as ADS-B.
- **Tracking: Lost Velocity Data and Small Speed Errors** — Several details of the airborne velocity message were decoded incorrectly. A magnetic heading of exactly north was treated as unavailable. A message missing one speed component was discarded with its vertical rate. A message without a speed cleared the aircraft's last known speed and vertical rate. The largest GNSS to barometric altitude difference (3,150 ft or more) was treated as unavailable. Ground speed was cut to the whole knot below instead of rounded, so it read up to 1 knot low. Each is now handled as the standard defines, and a value a message does not carry keeps its last known value.
- **Tracking: LNAV Shown as Off When Not Reported** — The ADS-B target state message reports the autopilot modes only when a status bit says they are valid. LNAV was read even when they were not, so it showed as off for aircraft that did not report their modes. It now shows as unknown, like the other modes. The TCAS status in the same message is independent of that bit and is still read.
- **Decoding: Positions at Exactly 87° Latitude** — The longitude zone count used in position decoding was off by one at exactly 87° north or south. It now matches the standard.

## [0.8.3] — 2026-10-24

### Changed

- **REST API and Web Map: Compressed Responses and Uncached Live Data** — The daemon now compresses what it serves, using the Brotli and gzip support built into .NET, so the Web Map's first load over the local network is about a third of its former size (the map library alone drops from about 1 MB to under 400 KB) and API responses shrink by more. Brotli is used whenever the client offers it, which browsers do over HTTPS; on plain HTTP they receive gzip. The live connection the Web Map uses for updates is left uncompressed. Every API response now also carries `Cache-Control: no-store`, so no browser or proxy can show stale aircraft data from a cache. `Uptime` in `/api/v1/stats` and `/api/v1/health` now counts from when the daemon started, matching the session duration it logs on exit, rather than from when its web server came up a few seconds later.

### Fixed

- **Web Map: Aircraft Missing Across the 180° Meridian** — A map view that crossed the 180° meridian, or one zoomed out far enough to show the world more than once, could come up empty or stop following the view. MapLibre reports such views with longitudes past ±180 (an eastern edge of 188°, for example), which the server rejected: the initial load and the refetch after a reconnect got an error instead of aircraft, and live updates kept going to the previous view. A wide screen at zoom 2 centered on Europe was already enough to trigger it. The Web Map now folds its view into range before sending it, and the server, the live updates and the heatmap all understand a box whose western edge is east of its eastern edge as one that crosses the meridian. The Sky View uses the same rule, so a receiver near the meridian now subscribes to its own range instead of the whole world.
- **Aircraft Photos: Tracked Aircraft Only, Cached for at Most 12 Hours** — `/api/v1/aircraft/{icao}/photo` looked up any ICAO address it was given, so anyone who could reach the daemon could use it as a general Planespotters lookup, at one upstream request per address and with memory that grew with every new one. It now answers 404 for an aircraft that is not being tracked, without contacting Planespotters. Cached photo metadata also had no age limit, so an aircraft tracked continuously for more than a day, such as one parked within range of the receiver, kept metadata past the 24 hours Planespotters allows. Entries now expire after 12 hours and are fetched afresh.
- **REST API: Stricter Validation and Consistent Errors** — Bounding boxes with a longitude outside ±180 on either edge, or with a value of `NaN`, were accepted and silently returned nothing; they now return 400 with the reason. A repeated query parameter, such as `type=Position&type=State`, is now an error rather than reduced to its first value, and `sections=,` returns every section like an empty `sections=` instead of none. Unknown `/api` routes and methods other than GET now answer with the same `{"Error": "..."}` body as every other error instead of an empty one, and error messages no longer format numbers in the server's locale (`48,5` on a Hungarian system). History responses now read their sequence ID range and their entries at the same instant, so a client using `MaxSequenceId` as its polling cursor can no longer receive an entry twice.
- **Tracking: Aircraft Track Lost When Heard Just Before Timing Out** — An aircraft that sent a message at the very moment the tracker was removing timed-out aircraft could be removed anyway, even though it had just been heard. Its track history and decoded details were discarded, the Web Map dropped it and its cached photo, and its next message started it again from nothing. It was rare, because the message had to arrive within the same instant as the cleanup, but it hit exactly the aircraft at the edge of coverage that come and go. The tracker now removes an aircraft only if it has not been heard from since it was judged timed out.

### Documentation

- **REST API Reference Corrected** — `docs/API.md` described several things the API does not do. The health endpoint never returns 503, a disabled history type has its fields set to `null` rather than omitted, `FramesPerSecond` is the average since the receiver started rather than the current rate, `FlightLevel` is never `null`, and `apiEnabled: false` also turns off the Web Map. It also gave wrong unit values in its examples. These are corrected, the 500 and 502 status codes and the 10,000 cap on `limit` are documented, and the polling example now uses the last received entry as its cursor. The JSON broadcast examples in `docs/BROADCAST.md` had the same altitude and speed errors and are corrected too.

## [0.8.2] — 2026-09-27

### Changed

- **Web Map: Aircraft Drawn on the GPU** — Tilting and rotating the map are now smooth, most noticeably on phones, where they were slow and the aircraft moved in visible steps. Aircraft are drawn by the map's own WebGL layer instead of being repositioned on every frame. Nothing about the map looks different.

## [0.8.1] — 2026-09-19

### Added

- **Web Map: Aircraft at Their Real Height** — Tilting the map now shows where aircraft actually are. Each is drawn at its height above the ground, with a thin line down to its own silhouette lying flat on the ground it is over, and the selected aircraft's trail becomes a ribbon, the flight path drawn at altitude with a translucent curtain hanging from it down to the ground track, so a climb or descent can be read straight off the map. A level map is unchanged. A `Height scale` setting controls how much the height is exaggerated, defaulting to twice true scale because a real height is only a few pixels on a wide view, with `×1` for true scale and `×5` for very wide ones; the readout shows `ALT ×2` or `ALT ×5` whenever the map is drawing aircraft higher than they are. Aircraft higher than the camera itself are above the horizon and cannot be drawn in the air: they keep their shadow and a line running out of the frame rather than being drawn back down onto the ground, which would put them somewhere they are not. Heights follow the same source as the trail and the Sky View, barometric where reported and geometric otherwise.
- **Web Map: Map View Readout** — The map now carries the same kind of readout the Sky View has, in the top-left corner: how far across the visible map is, how much ground it covers, the bearing and distance from the receiver to the center of the map, how many aircraft are on screen against how many are tracked, and the farthest the receiver has heard. The map previously had no scale indication of any kind. Distances follow the selected distance unit and the area follows it into its square (nm², km², mi²). The map's bearing appears only while it is rotated away from north, and the area is withheld while the map is tilted, where the top of the screen can be looking at the horizon and no honest figure exists.

### Fixed

- **Statistics: Negative CRC Error Count on Multi-Device Receivers** — `/api/v1/stats` reported a negative `CrcErrors` figure and a frames-per-second rate too high by the number of attached devices. The confidence tracker is deliberately shared across all SDR devices, so that MLAT can mark an ICAO confident for every device at once, but its frame counters were being summed once per device. That made `ValidFrames` exceed `TotalFrames`, and the CRC error count is derived from the difference between them. Single-device receivers were unaffected, which is why it went unnoticed. The per-device debug log carried the same confusion, printing receiver-wide confidence counters under each device's name, and now says which they are.
- **Web Map: Readout Clipped by the Control Panel** — The Sky View's readout ran underneath the search and settings panel on any screen narrower than about 1200 pixels, taking its sun, moon and exclusion counts with it, and the new Map View readout did the same. Both rows are now bounded by the space actually available between the aircraft list and the control panel, and drop readings one at a time until what remains fits, keeping the most useful ones: the aircraft count and camera heading in the Sky View, the visible span in the Map view. Where not even one reading fits, the row is hidden rather than drawn where it cannot be read.
- **Web Map: Sky View Coverage Ribbon Units** — The coverage ribbon's distance scale now follows the selected distance unit instead of always being labeled in nautical miles, so a reading taken in kilometers or statute miles is no longer short by the conversion factor. The scale also rounds in the selected unit (50 nm, 100 km, or 50 mi), so its ticks stay round numbers rather than becoming a converted nautical-mile step.

### Documentation

- Rewrote the [Web Map Guide](docs/WEBMAP.md) around the two views, covering the configuration a map needs, every control in the settings panel, and a troubleshooting section for a map that stays empty or will not start. The screenshots were retaken, with separate ones for the Map and Sky settings.

## [0.8.0] — 2026-09-12

### Added

- **Web Map: Sky View** — A second Web Map view showing where aircraft are relative to the receiver rather than on a flat map. A virtual camera at the configured receiver position looks along a heading you control; aircraft are placed by bearing and elevation angle, sized and hazed by distance. A `Map` / `Sky` control in the control panel switches views, sharing the selection, detail panel, and search with the map. Elevation angles account for receiver altitude, the curvature of the Earth, and atmospheric refraction, so distant traffic sits correctly near the horizon instead of floating above it; aircraft hidden by the curve are marked on the horizon line rather than silently dropped, and their true elevation is still reported. A coverage ribbon along the foot of the view shows how far the receiver has actually heard in each 5° of bearing over the last 24 hours, on a labelled distance scale. An optional 360° flattened mode shows the whole sky at once. Drawn on a plain 2D canvas, so it works where the WebGL map cannot start. Requires a configured receiver location; `receiver.altitude` is optional but improves accuracy for elevated sites.
- **Web Map: Sky View Sun and Moon** — The Sky View now marks where the sun and the moon really are, the moon with its current phase and its lit side facing the sun, and tints the sky to follow the sun's height from daylight through twilight to night. Positions are the apparent ones an observer sees, corrected for parallax and refraction, and a body stays drawn until its upper limb has set, so the sun does not vanish the moment its centre reaches the horizon. Because the aircraft colours were chosen against a pale sky, chip outlines now follow the sky's brightness and stay findable after dusk. Both are labelled on the view and reported in the heading readout while they are up. The markers and the sky colouring are separate settings, `Sun and moon` and `Day and night sky`, both on by default.
- **Web Map: Sky View Touch Gestures** — Pinch to change the Sky View's field of view on a touch device, where it previously had to be set from the settings panel, and double-tap to reset the camera. Both are detected from pointer events so mouse and touch behave identically. A pointer taken away by the browser mid-gesture (a system edge swipe, for instance) now ends the gesture instead of leaving the camera turning with nothing on screen.
- **Device Tuner Coverage** — `aeromux device --verbose` now lists the frequency ranges each receiver's tuner can reach, and flags a tuner that cannot reach 1090 MHz as unusable for Mode S. Such a receiver previously aborted the entire verbose listing with an unhandled error; it is now reported inline and the remaining devices are listed normally.

### Changed

- **Web Map Aircraft List Performance** — The aircraft list now renders only the rows on screen, so the cost of displaying it follows the height of the panel rather than how many aircraft are in range: roughly 30 rows on a desktop panel whether 200 or 1 500 aircraft are being received, where previously every one became a row. The map also stops re-rendering the list on every pointer movement over an aircraft. Sorting, selection, and scrolling are unchanged.
- **Web Map Viewport Subscription** — Which aircraft the server pushes is now explicit client-side state rather than being derived from the map camera, so the two views can request different regions over the same API. Map behaviour is unchanged.
- **RtlSdrManager 0.8.0** — Upgraded the RtlSdrManager RTL-SDR access library from 0.7.1 to 0.8.0. Using a device after it has been closed is now a hard error inside the library rather than undefined behaviour; most importantly, starting a read on a closed device no longer terminates the process. Aeromux's sample callback now ends quietly when a device is closed mid-callback, so shutting down a device that did not stop within its timeout no longer logs a spurious processing error. The dropped-sample counter is now updated atomically.

### Fixed

- **Web Map Flight Profile Altitude** — The flight-profile chart now falls back to geometric (GNSS) altitude when an aircraft reports no barometric altitude. Such aircraft previously contributed no altitude points at all, leaving gaps in the chart.
- **Minimum Tuner Gain Accepted** — A `tunerGain` of `0` is now accepted on R820T/R828D receivers, where it is the tuner's lowest gain step. The driver previously reported 28 of the tuner's 29 gain steps and rejected `0`, so `aeromux device --verbose` under-reported the available gains and a valid configuration was refused at device open.

## [0.7.7] — 2026-07-25

### Added

- **RTL-SDR Dead-Stream Detection** — Each SDR device now reports asynchronous read errors surfaced by the driver. If a device stops streaming mid-run, a warning is logged (with the underlying error) instead of the stream ending silently.
- **RTL-SDR Tuner Gain Validation** — A configured manual `tunerGain` that is not a step supported by the tuner is now rejected at device open with a clear message listing the supported gains for that device, instead of surfacing a bare library error.

### Changed

- **Web Map Range Outline Window** — The receiver coverage range outline now reflects the farthest aircraft received over the last 24 hours instead of 4, giving a fuller, more stable coverage picture that better survives quiet periods.
- **RtlSdrManager 0.7.1** — Upgraded the RtlSdrManager RTL-SDR access library from 0.6.3 to 0.7.1. Device shutdown is now crash-safe: an error that stops asynchronous sample reading is logged and no longer escapes teardown or terminates the process. The tuner-gain conversion was corrected to round to the nearest supported step (tenths of a dB), so the configured gain maps to the exact value the hardware applies.

### Fixed

- **Clearer "No RTL-SDR Device" Message** — When SDR sources are configured but no RTL-SDR hardware is present, Aeromux now fails fast with an actionable message (check the USB connection, install librtlsdr, run `aeromux device`). Previously, with the upgraded driver's changed enumeration behaviour, this could surface as a generic device error.
- **Clearer RTL-SDR Device Errors** — When a device can't be opened — most often because the configured device index doesn't match a connected receiver — Aeromux now explains what went wrong and how to fix it (check the device index, run `aeromux device`) instead of printing a technical error, and keeps the log tidy. The `live` and `daemon` commands report it the same way.

## [0.7.6] — 2026-07-18

### Added

- **Daemon: Automatic Database Updates** — The daemon can now keep the aircraft metadata database current on its own, downloading and verifying newer releases and applying them **without a restart** by hot-swapping the live database. Newly seen aircraft are enriched from the updated data immediately (already-tracked aircraft keep theirs until they cycle out); on a fresh host the first check downloads a database and brings enrichment live. Superseded files are pruned after each update. Configured under a new `database.autoUpdate` YAML section — daemon-only, on by default, but dormant unless `database.enabled` is true and the directory is writable. Checks run at startup and every 24 h (configurable); failures are logged and retried and never disturb a running receiver.
- **Web Map: Active Database Indicator** — When database enrichment is active, the Web Map header subtitle now reads "Web Map (vX.Y.Z) with Database Enrichment (\<db-version\>)", showing which database vintage is loaded. It updates live over the existing SignalR channel when the daemon hot-swaps a new database, with no page reload.

### Changed

- **Web Map Heatmap Push Performance** — Serving the traffic-density heatmap now costs the daemon far less CPU. The overlay is computed once and shared across all connected clients and refreshed at most every 15 seconds, instead of being rebuilt for every client every second; interactive changes still repaint immediately and an idle overlay does no work. On constrained hosts such as a Raspberry Pi this cuts the CPU cost of a viewed heatmap by roughly an order of magnitude.

### Fixed

- **Web Map: Range Outline Covering Range Rings** — The receiver coverage-range outline could render on top of the range rings and their distance labels, obscuring them. The outline is now anchored beneath the range-ring layers regardless of which overlay loads first, so the rings and labels stay readable.
- **Web Map: Heatmap Lingering After Toggle-Off** — Turning off the traffic-density heatmap could leave it frozen inside the previous viewport when a server frame already in flight repopulated the just-cleared overlay. The client now ignores heatmap frames that arrive after the overlay is toggled off, and re-enabling it renders immediately.

## [0.6.2] — 2026-04-25

### Fixed

- **Memory Leak: ICAO String Cache** — Fixed unbounded growth of the ICAO hex string cache in `ValidatedFrameFactory`. In AP mode (DF 0/4/5/16/20/21), every noise frame produced a random ICAO that was cached permanently. With multiple factory instances (2 per SDR device + 1 per Beast connection), caches could grow to ~2.3 GB over hours of operation. The cache now clears when it exceeds 65,536 entries (~4.5 MB). Real aircraft ICAOs are re-cached within seconds.
- **Memory Leak: Unbounded Subscriber Channels** — Fixed unbounded memory growth in `ReceiverStream` and `BeastStream` subscriber channels. When a TCP broadcast client was slow or unresponsive, its subscriber channel accumulated frames indefinitely (~1 GB/hour at 300 fps). Subscriber channels are now bounded to 50,000 frames (~20 MB) with a drop-oldest policy. The `AircraftStateTracker` processes frames in microseconds and is unaffected by the limit.
- **Slow TCP Client Starvation** — Fixed a single slow TCP client blocking the entire broadcast loop, starving all other clients. `WriteAsync` had no timeout, so a client with a full send buffer would block indefinitely. Added a 5-second per-client write timeout that disconnects unresponsive clients with a warning log, allowing other clients to continue receiving data.
- **Derived Geometric Altitude Crash** — Fixed `ArgumentOutOfRangeException` crash when the derived geometric altitude (barometric + delta from TC 19) exceeded the valid range [-2000, 126700] feet. The unhandled exception killed the `AircraftStateTracker` consumer task, causing all aircraft to expire and the web map to go empty while Beast/SBS broadcasts continued working. The derivation now validates the sum before creating the `Altitude` value. The consumer task also catches handler exceptions to prevent any single bad frame from killing the tracking pipeline.
- **Surface CPR Southern/Western Hemisphere** — Fixed incorrect surface position decoding for receivers in the Southern or Western Hemisphere. C#'s `%` operator on negative coordinates preserves the sign, producing wrong latitude/longitude zone indices. This shifted decoded surface positions by one zone width (~1.5° latitude / ~90 NM). Added a `CprMod` helper that always returns positive modulo results.
- **Altitude/Velocity Unit Conversion Rounding** — Fixed unit conversions in `Altitude` and `Velocity` value objects truncating instead of rounding. `(int)` cast truncated toward zero, causing systematic 1-unit drift (e.g., `FromFeet(35000).Meters` → `FromMeters(10668).Feet` = 34999 instead of 35000). Affects TC 20-22 GNSS geometric altitudes (decoded in meters, stored as feet) and all metric display values in the web map and REST API. Replaced `(int)(...)` with `(int)Math.Round(...)` in all conversion paths.
- **Supersonic Velocity Crash** — Fixed `ArgumentOutOfRangeException` thrown when parsing TC 19 supersonic velocity subtypes (2 and 4). The `Velocity` value object capped at 1500 knots but supersonic encoding can produce up to 4088 knots per axis. Every supersonic velocity message threw, was caught as an "unexpected error," and the message was silently dropped. Raised the cap to 4096 knots to cover the full supersonic encoding range. Ground speed magnitudes above 4096 (both axes simultaneously maxed) are rejected as corrupt data. Also removed workaround guards in Comm-B handlers that silently dropped valid BDS 5,0 velocities in the 1501-2046 knot range.
- **Web Map Push Service Silent Failures** — Added error logging to `MapHubPushService.ExecuteAsync` catch block. Previously, all exceptions were swallowed silently, causing the web map to stop updating with no diagnostic trail.
- **Web Map Slow Client Blocking** — Added a 5-second per-client push timeout in `MapHubPushService`. A single slow SignalR client could block the sequential push loop, delaying updates to all other clients. Timed-out clients are skipped for the current tick and self-heal on the next push cycle.
- **History API Unbounded Limit** — Clamped the `?limit=` query parameter on the history API endpoint to a maximum of 10,000 entries. Previously, any positive integer was accepted, allowing a single request to serialize unbounded history data.
- **Static File Missing Cache Headers** — Added `Cache-Control: public, max-age=86400` to embedded web map static files. Browsers previously re-fetched unchanged assets (JS, CSS, fonts) on every page load.
- **Database Asset Filename Validation** — Added path traversal validation for the database asset filename before passing it to `InstallDatabase`. Rejects filenames containing invalid characters, directory traversal sequences (`..`), or path separators.
- **Daemon Shutdown Delay** — Removed redundant explicit `StopAsync` call before `DisposeAsync` on the web application. `DisposeAsync` internally calls `StopAsync`, so the explicit call added an unnecessary shutdown timeout delay.
- **Non-Loopback Bind Address Warning** — Added a log warning when the daemon binds to a non-loopback address (including the default `0.0.0.0`), informing that services are accessible from the network.
- **Database Download ANSI Escape Codes** — Fixed garbled progress output when stdout is redirected (piped to file, CI runners, non-VT terminals). ANSI cursor movement codes are now only emitted to TTY terminals; redirected output prints progress at 25% intervals instead.

## [0.6.1] — 2026-04-17

### Changed

- **Web Map Detail Panel Layout Persistence** — Section expand/collapse and "show more" toggle states in the aircraft detail panel now persist when switching between aircraft. Previously, selecting a new aircraft reset all sections to their default state. Added a "Reset layout" link in the detail toolbar to restore defaults.
- **Enum Validation Performance** — Replaced all 55 `Enum.IsDefined` reflection calls in the Mode S parsing hot path with zero-allocation range checks and pre-computed lookup tables, eliminating boxing allocations and reflection overhead per message parse.
- **Frame Extraction Performance** — Reuse pre-allocated buffers during preamble detection phase testing, eliminating ~99% of short-lived byte array allocations in the signal processing hot path.
- **TCP Broadcast Performance** — Replaced per-frame client list copying with a copy-on-write volatile snapshot, eliminating up to 3,000 list allocations per second across Beast, JSON, and SBS broadcasters.
- **Encoder Output Performance** — Replaced per-frame `byte[]` allocations in Beast, JSON, and SBS encoders with reusable instance buffers returning `ReadOnlyMemory<byte>` slices, eliminating 5,000–10,000+ short-lived allocations per second across all three broadcast formats.
- **Database Lookup Performance** — Removed unnecessary lock and pre-created the parameterized SQLite command in the aircraft database lookup service, eliminating per-lookup command allocation and lock overhead.
- **Aircraft Tracking Performance** — Changed the aircraft state dictionary from string to `uint` ICAO keys, replacing per-lookup 6-character string hashing with single-instruction integer hashing on the 1,000+/sec update hot path.
- **Comm-B Parsing Performance** — Replaced per-message `byte[]` allocation and `Array.Copy` for the 7-byte MB field with a zero-copy `ReadOnlySpan<byte>` slice into the existing frame data, eliminating a heap allocation per DF 20/21 message.
- **Update Event Performance** — Replaced `EventHandler<AircraftUpdateEventArgs>` with `Action<Aircraft, Aircraft>` for the aircraft update event, eliminating a per-frame heap allocation on the 1,000+/sec update path.

### Added

- **Web Map Aircraft Category Dots** — Colored category indicator dots in the aircraft list and detail panel header, matching the map marker colors: blue for normal, green for military, red for privacy (LADD/PIA). Category colors are defined as shared CSS classes used across the legend, list, and detail views.
- **Web Map Category-Colored Trail** — Aircraft position trail now uses the selected aircraft's category color (dark blue for normal, dark green for military, dark crimson for privacy) instead of a fixed blue gradient.
- **Web Map Range Outline** — Coverage polygon connecting the farthest aircraft positions received in each 5-degree bearing sector over the last 4 hours. Positions beyond 300 nm are discarded. Rendered as a semi-transparent fill with a dashed border below the range rings. On by default, toggleable from the settings panel. The toggle is disabled when receiver location is not configured. Resets on restart.
- **CPR Position Validation** — Three-layer position validation to eliminate wildly incorrect aircraft positions (appearing as long straight lines across the map) caused by CPR global decode errors from bit corruption passing CRC. Layer 1: receiver range check rejects decoded positions beyond 300 NM from receiver (skipped when receiver location is not configured). Layer 2: speed/distance plausibility check validates that position changes are physically possible given elapsed time and aircraft speed. Layer 3: position persistence counter requires 4 consecutive implausible positions before overwriting a known good position, preventing single bad decodes from corrupting tracks.

### Fixed

- **ICAO Confidence Tracker Thread Safety** — Fixed `NullReferenceException` crash in `IcaoConfidenceTracker.CleanupExpired` caused by concurrent dictionary access from multiple SDR device workers sharing the same tracker instance. Added `ReaderWriterLockSlim` to allow concurrent read access on the high-frequency `IsConfident` hot path while serializing write operations.
- **Beast Timestamp MLAT Precision** — Fixed mlat-client reporting "clock unstable" by deriving 12 MHz Beast timestamps from the cumulative RTL-SDR sample counter instead of wall-clock time. The previous approach captured `DateTime` at USB buffer callbacks, introducing 1–5 ms of OS scheduling jitter — far exceeding MLAT's ~1 μs requirement. The new pipeline computes `(cumulative_sample_count + sample_offset) × 5` at frame extraction, producing timestamps tied to the radio crystal oscillator with zero jitter. BeastEncoder now passes through the pre-computed 12 MHz value directly. BeastParser preserves the 48-bit wire timestamp for relay scenarios.
- **Beast Parser Stream Resynchronization** — Fixed BeastParser silently consuming valid frame data when encountering unknown Beast message types. The parser now skips unrecognized types and rescans for the next frame start marker, preventing stream desync from corrupted or unsupported messages.
- **MLAT Feedback Loop** — Fixed MLAT-computed positions being re-broadcast on the Beast output port (30005), causing mlat-client to warn "Ignored N messages with MLAT magic timestamp". The Beast broadcaster now filters out `FrameSource.Mlat` frames, preventing synthetic DF 17 positions received from mlat-client (port 30104) from looping back.
- **Web Map Selected Aircraft False Expiration** — Fixed the aircraft detail panel incorrectly showing `[EXPIRED]` when panning the map away from the selected aircraft's position. The viewport-based removal logic was sending `AircraftRemoved` for aircraft that simply left the visible area, which the client interpreted as a true expiration. The selected aircraft is now excluded from viewport-based removal, with its lifecycle managed solely by the dedicated selected-aircraft block that checks the actual tracker state.
- **Velocity Flickering Between TC 19 Subtypes** — Fixed Track and Heading values nullifying each other when an aircraft alternates between TC 19 subtype 1-2 (ground speed → Track) and subtype 3-4 (airspeed → Heading) messages. The handler's `with` expression overwrote both fields on every message, setting the one not provided by the current subtype to `null`. This caused flickering in the detail panel and map icon rotation defaulting to north when only Heading was available. The handler now uses a second `with` that only updates the directional field the current subtype provides, preserving the other from previous state.

## [0.5.0] — 2026-04-03

Initial public release.

### Added

- **Mode S and ADS-B Decoding** — All Mode S downlink formats (DF 0–24), ADS-B Extended Squitter message types (TC 1–31), and Comm-B data registers (BDS 1,0 through BDS 6,5). Covers identification, position, altitude, speed, heading, vertical rate, autopilot, meteorology, ACAS/TCAS, transponder capabilities, and data quality.
- **Multiple RTL-SDR Support** — Simultaneous operation of multiple RTL-SDR USB receivers with independent gain, PPM correction, and preamble threshold settings per device. Automatic frame aggregation and deduplication.
- **Beast TCP Input** — Connect to one or more external Beast-compatible servers (dump1090, readsb, or another Aeromux instance). Can be used alone or combined with local SDR devices. Automatic reconnection with exponential backoff.
- **Unified Input Model** — SDR devices and Beast TCP sources can be freely combined. All sources are merged into a single deduplicated stream.
- **Beast Output** — Binary protocol compatible with dump1090, readsb, and MLAT networks.
- **SBS/BaseStation Output** — CSV text protocol compatible with Virtual Radar Server. AIR, ID, and all eight MSG subtypes.
- **JSON Output** — Streaming NDJSON with consolidated aircraft state. Per-aircraft rate limiting (1 update/sec). Schema matches the REST API for client compatibility.
- **REST API** — Read-only JSON API: aircraft list, aircraft detail (10 sections, selectable), position/altitude/velocity history, receiver statistics, and health check. Per-client rate limiting.
- **MLAT Support** — Receives multilateration position data from mlat-client for aircraft that do not broadcast ADS-B positions.
- **Live Mode (TUI)** — Interactive terminal interface with sortable aircraft list (F1–F6), ICAO/callsign search with highlighting, detail view with field search and jump-and-highlight navigation, and display unit switching (distance, altitude, speed).
- **Daemon Mode** — Background service for continuous, unattended operation with all data served over the network.
- **Aircraft Database Enrichment** — Integration with the [aeromux-db](https://github.com/aeromux/aeromux-db) database for registration, operator, manufacturer, and aircraft type metadata. Built-in commands for download, update, and integrity verification.
- **Device Discovery** — `aeromux device` command to list detected RTL-SDR hardware with optional detailed tuner parameters.
- **Configuration** — Single YAML file with per-setting CLI override (CLI > YAML > Default). Fully documented example configuration with sensible defaults.
- **Cross-Platform** — Self-contained, single-file executables for macOS (Intel and Apple Silicon) and Linux (x64 and ARM64, including Raspberry Pi 4/5).
- **Documentation** — [CLI Reference](docs/CLI.md), [TUI Guide](docs/TUI.md), [REST API Guide](docs/API.md), [Broadcast Guide](docs/BROADCAST.md), [Deployment Scenarios](docs/SCENARIOS.md), and [Architecture Guide](docs/ARCHITECTURE.md).
